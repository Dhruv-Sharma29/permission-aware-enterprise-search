# 05 — Evaluation

## What question the evaluation answers

> **Does anything derived from a document reach a user who can't read it, through any surface? And
> given that it doesn't, how good are retrieval and answers for each user, on held-out questions?**

The order matters. Leak counts are reported for every mode and every answerer, and quality numbers
are computed only over what each user is allowed to answer. A system that answered well by leaking
would show up as a non-zero leak count, not as a high score.

## Units, splits, and "answerable"

- **Unit:** a (question, user) pair. All 12 users ask all 114 questions: 1,368 pairs.
- **Split:** by SHA-1 of the question id, parity → dev/test (`eval/run.py: split_of`). Dev: 59
  questions, 708 pairs. Test: 55 questions, 660 pairs.
- **Answerable for a user:** the question has a gold answer **and** the user can read at least one
  gold document (oracle). Test: 156 answerable, 504 not. Dev: 214 / 494.
- **Tuned on dev, reported on test:** the extractive threshold, the archived-document weight, two
  extractive fixes, and the LLM prompt. The test split was run once with the LLM (README § Design
  notes; PLAN.md M4 decision).

Consequence of the hash split: the **test split contains no role-conflicting and no
shared-by-name questions**. Both landed in dev (`eval.json` § `supported_by_category`). Test also
has only one scanned question (2 answerable pairs) and one injection probe (2 pairs).

## Metrics

| Metric | Definition (`eval/run.py`) |
|---|---|
| recall@5 | Over answerable pairs: a readable gold doc is among the first 5 distinct doc ids |
| MRR@10 | Over answerable pairs: 1 / rank of the first readable gold doc in the top 10, else 0 |
| Retrieval leaks: doc | Hits (top 10) whose document the oracle says the user can't read |
| Retrieval leaks: content | Occurrences of the user's `forbidden_values` in hit text |
| Supported answer rate | Answerable pairs answered (not abstained) with a gold string in the answer |
| Appropriate abstention rate | Not-answerable pairs where the answerer abstained |
| Unsupported answer share | Of all non-abstaining answers, those not (answerable and correct) |
| Content / citation leaks (answers) | Forbidden values in answer text / cited docs the user can't read |
| Citation checks | Uncited answers; answers with a number not in the cited text; correct-but-citation-lacks-answer; invalid passage numbers |
| Search latency | Wall time of one `search()` call, p50/p95, ms |

## Results: retrieval (test, 660 pairs, 156 answerable)

| Mode | recall@5 | MRR@10 | Unauthorized docs | Forbidden values | p50 / p95 ms |
|---|---|---|---|---|---|
| Keyword (Postgres FTS) | 0.885 | 0.815 | 0 | 0 | 9.9 / 16.8 |
| **Vector (BGE-base, exact)** | **1.000** | **0.910** | 0 | 0 | 11.8 / 18.3 |
| Hybrid (RRF, k = 60) | 0.962 | 0.886 | 0 | 0 | 21.7 / 34.4 |
| Hybrid, no archive penalty | 0.962 | 0.886 | 0 | 0 | 21.7 / 34.8 |

Source: `results/summary/eval.json` § `test`. Dev, for comparison (`eval.json` § `dev`):

| Mode | recall@5 | MRR@10 |
|---|---|---|
| Keyword | 0.916 | 0.887 |
| Vector | 1.000 | 0.897 |
| Hybrid | 0.986 | **0.950** |

What the numbers say:

- **On test, vector alone beats hybrid on both metrics.** On dev, hybrid had the best MRR (0.950 vs
  0.897) while vector kept the best recall. So "vector is better" holds on held-out questions but
  isn't uniform across splits. With 55 test questions, the MRR gap between vector and hybrid is
  small enough that the ranking of the two shouldn't be over-read.
- **Keyword's losses are concentrated in engineering** (test recall@5 0.714 vs vector 1.000) and
  confidential (0.875). README attributes this to OCR text that runs words together and to
  paraphrased questions. The per-category numbers are consistent with that, but no error analysis
  file records it.
- **The archive penalty had no effect** (identical rows). There is one archived document in the
  corpus, so this was barely tested ([07](07-risks.md) § R1).
- **Hybrid is still the default** in `/search` and in the answer path (`answer/service.py`). The
  LLM's two retrieval-limited questions on test (below) are engineering questions, the category
  where hybrid recall@5 is 0.857 and vector's is 1.000. Switching the answer path to vector is the
  obvious next experiment, and it would have to be decided on dev ([06](06-roadmap.md)).
- **No reranker was tried.** PLAN.md M3 asked for the attempt to be recorded either way.

## Is the LLM gain real?

`eval/run_llm.py` reports an exact two-sided McNemar test on discordant outcomes, two ways:

| Split / prompt | Per pair: LLM-only vs extractive-only, p | Per distinct (question, passages) input, p |
|---|---|---|
| dev v1 | 29 vs 11, p = 0.0064 | 12 vs 1, p = 0.0034 |
| dev v2 | 29 vs 0, p reported as 0.0 (rounded to 4 places) | 12 vs 0, p = 0.0005 |
| **test v2** | 14 vs 1, p = 0.001 | **6 vs 1, p = 0.125** |

Source: `paired.supported` in each `llm_answers_*.json`.

Pairs that share a question mostly share passages (users with the same access often get identical
top-5s), so per-pair counts overstate independence. The distinct-input count is the closer
approximation of an independent unit, and **on test it is not significant**. The direction agrees
with dev, but dev was used to choose the prompt. The honest summary: *the LLM never did worse on
authorization or abstention, and was better on tables and OCR text, but 7 discordant inputs can't
establish the size of the gain.*

## What not to claim

- "Leak-proof." The claim is 0 observed in this suite.
- "Hybrid retrieval." The best measured mode on test is vector. Hybrid is the code default.
- "The LLM is significantly better." Not on test at the distinct-input level.
- "The LLM resists prompt injection." It was never shown forbidden data ([04](04-grounded-answers.md)).
- "Revocation in 58 ms." The guarantee is per request. The milliseconds are request latency.
